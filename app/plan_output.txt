```python
class UndoManager:
    """Command-pattern undo/redo backed by SQLite."""
    
    MAX_HISTORY = 50  # UNDO-3: at least 50 levels
    
    def record(self, action_type: str, before_state: dict, after_state: dict, db_path=None):
        """Record an action. Clears any redo stack (undone entries after cursor)."""
        
    def undo(self, db_path=None) -> dict | None:
        """Revert the most recent non-undone action. Returns before_state or None."""
        
    def redo(self, db_path=None) -> dict | None:
        """Re-apply the most recently undone action. Returns after_state or None."""
        
    def _apply_state(self, state: dict, db_path=None):
        """Apply a state snapshot: update constants, elements, doors, outline chain."""
        
    def _prune(self, db_path=None):
        """Keep at most MAX_HISTORY entries."""
```

The `before_state`/`after_state` JSON captures the minimum delta needed to restore: `{"constants": {"BED_WIDTH": 6.333}, ...}` for constant changes, `{"elements": [{"id": 5, ...}]}` for element changes, etc.

## Phase 6: Outline Chain Editing

**Requirements addressed:** ENG-11, API-16 through API-19, OE-1 through OE-3, DT-2 through DT-4 (10 requirements)

### New Files

**`app/outline_solver.py`** (~300 lines)

This is the most architecturally significant new module. Since `floorplan/geometry.py` runs the closure solver at module scope and we cannot modify it, we need a parallel solver in `app/`.

```python
def chain_offset(chain: list, start_brg: float = 0.0) -> tuple[float, float, float]:
    """Walk chain entries from (0,0). Returns (delta_E, delta_N, exit_brg).
    
    Reimplements floorplan.geometry._chain_offset for use in the app solver.
    """

def solve_closure(chain_f5_to_f18: list, corner_sw_r: float) -> tuple[float, float]:
    """Solve for d_F2_F5 and d_F18_F1 given the middle chain.
    
    Returns (d_F2_F5, d_F18_F1).
    Raises ClosureError if the chain cannot close.
    """

def validate_chain(modified_chain: list, corner_sw_r: float) -> dict:
    """Validate a proposed chain modification.
    
    Returns {"valid": bool, "closure_error": float, "d_F2_F5": float, "d_F18_F1": float}
    """

def apply_chain_modification(seq: int, updates: dict, db_path=None) -> dict:
    """Update an outline chain segment and re-solve closure.
    
    updates: {"dist_or_radius": float, "sweep": float}
    Returns updated segment + closure info.
    """

def add_chain_point(position: int, point_name: str, seg_type: str, 
                    params: dict, db_path=None) -> dict:
    """Insert a new F-point, splitting a segment. Re-solve closure."""

def remove_chain_point(seq: int, db_path=None) -> dict:
    """Remove a chain point, merging adjacent segments. Re-solve closure."""

def solve_for_constraint(constraint: dict, db_path=None) -> dict:
    """Solve chain parameters to satisfy a geometric constraint.
    
    constraint: {"point_a": "W20", "point_b": "W1", "metric": "clear_span", "target": 23.5}
    Returns {"feasible": bool, "chain_updates": [...], "computed_value": float}
    """
```

**Key design:** The solver reads the current chain from the database, applies modifications, runs the closure computation (reimplemented from `_chain_offset` logic -- this is a pure math function, not importing from `floorplan/geometry.py`), and if valid, writes back to the DB. The engine then reloads modules which pick up the modified constants/chain.

For OE-3 (constraint-based editing), a simple Newton-Raphson or bisection solver iterates on chain parameters to satisfy a target distance constraint.

### Engine Integration

After outline chain modification, the engine must use the modified chain. Two approaches:
1. **Preferred**: The solver writes modified chain parameters back to the DB, then the engine's `compute_geometry()` reads from DB and patches constants as usual. The closure solver distances `d_F2_F5` and `d_F18_F1` are stored as derived constants.
2. The outline chain DB rows are used to reconstruct the chain list, which is injected into the geometry computation via constant patching.

## Anticipated Challenges

1. **Closure Solver Reimplementation (Phase 6):** The `_chain_offset` function in `floorplan/geometry.py` runs at module import time. Our parallel solver in `app/outline_solver.py` must produce identical results. Extensive cross-validation tests between the two are critical.

2. **Constant-to-Element Mapping (Phase 3/4):** Mapping a drag operation on, say, IW1 back to the correct constant (`IW1_OFFSET_FROM_W9`) requires a hand-maintained mapping table in `app/elements.py`. This table must be kept in sync with `floorplan/layout.py`'s computation logic.

3. **Module Reloading Side Effects (Phase 6):** When we modify outline chain parameters and call `compute_geometry()`, the module-scope closure solver in `floorplan/geometry.py` will run with the *original* constants, not our modified chain. We need to either: (a) patch the module-scope variables (`_d_F2_F5`, `_d_F18_F1`, `OUTLINE_CHAIN`) before reload, or (b) use our parallel solver to compute the correct values and inject them as constants. Approach (b) is safer.

4. **Frontend Module Splitting:** The current `app.js` is 1090 lines. Adding tools, canvas rendering, selection, and undo will push it past 3000+ lines if not split. The plan creates separate JS files (`canvas.js`, `tools.js`, `selection.js`, etc.) loaded as additional `<script>` tags. All modules share the global `App` namespace.

5. **Custom Element Overlay:** The engine computes base geometry from constants. Custom elements (user-added furniture, walls) exist only in the DB and are overlaid in the result. This dual-source model (constants-driven base + DB-driven overlay) must be carefully handled to avoid duplication or conflict.
